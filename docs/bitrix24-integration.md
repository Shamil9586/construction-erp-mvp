# Интеграция с Bitrix24

Документ фиксирует реально используемые механизмы Bitrix24 REST API для
встраиваемого (Local Application) приложения. Основано на официальной
документации apidocs.bitrix24.com (сентябрь 2026) и должно быть
перепроверено на тестовом портале перед продакшен-подключением —
см. раздел «Требует проверки на тестовом портале» в конце файла.

## 1. Модель приложения

Приложение регистрируется в Bitrix24 как **локальное приложение**
(Local Application) с типом встраивания через **placements** (виджет в
iframe) и/или как отдельная страница, открываемая из левого меню портала.
Это единственный официально поддерживаемый способ встроить собственный
frontend/backend в Bitrix24, не изменяя ядро платформы.

Источники:
- https://apidocs.bitrix24.com/api-reference/app-installation/local-apps/index.html
- https://apidocs.bitrix24.com/local-integrations/local-apps.html
- https://apidocs.bitrix24.com/settings/app-installation/local-apps/installation-master.html

## 2. Установка приложения (installation flow)

1. Администратор портала устанавливает приложение (из маркетплейса или как
   локальное — по `client_id`, полученному в «Разработчикам» → «Другое» →
   «Локальное приложение»).
2. Bitrix24 вызывает **событие `ONAPPINSTALL`** на `event_handler`-URL,
   зарегистрированный при создании приложения.
3. Обработчик события получает `POST`-запрос с полями `auth[access_token]`,
   `auth[refresh_token]`, `auth[expires_in]`, `auth[domain]`,
   `auth[member_id]`, `auth[application_token]`, `auth[scope]`.
4. Наш backend должен: создать/найти `Tenant` по `member_id` + `domain`,
   создать/обновить `BitrixInstallation` с зашифрованными токенами,
   вернуть `200 OK`.

**REQUIRES BITRIX24 TEST PORTAL VERIFICATION:** реальный вызов события от
тестового портала не проверялся (нет доступа к тестовому порталу в этой
среде разработки) — ни точные имена полей, ни наличие
`PLACEMENT`/`PLACEMENT_OPTIONS` в query при открытии embedded-страницы, ни
сам факт, что payload действительно совпадает с документацией на практике.
Реализация в `BitrixInstallController` написана строго по документированной
структуре, но НЕ считается production-secure сама по себе: у ONAPPINSTALL
как у самого первого контакта нет общедоступного криптографического
способа подтвердить, что именно ЭТОТ первый вызов пришёл от Bitrix24 (нет
предварительно разделённого секрета, с которым можно было бы сверить
именно его) — это ограничение самого протокола установки для первого
контакта, не пробел реализации. Подлинность самого первого вызова
дополнительно подтверждает последующий успешный обмен кода на токен через
`oauth.bitrix.info`, который тоже ещё не проверялся на реальном портале.

**Это ограничение касается ТОЛЬКО самого первого ONAPPINSTALL, а не
`application_token` в целом.** Ранее в этом документе была неверная
формулировка, будто хранение и последующая проверка `application_token`
— принципиально невозможны или являются фундаментальным ограничением
протокола. Это не так: согласно официальной документации Bitrix24,
`application_token`, полученный при установке, — штатный, документированный
механизм подтверждения того, что ПОСЛЕДУЮЩИЕ запросы (другие
event-хендлеры, а не сам первый ONAPPINSTALL) пришли от того же портала,
который ранее установил приложение. ХАРДЕНИНГ-ФИКС (integrity pass, п.5):
`application_token` из ONAPPINSTALL теперь сохраняется зашифрованным в
`BitrixInstallation.encryptedApplicationToken` (миграция
`20260915080000_bitrix_application_token`) как раз для этой цели — раньше
он после проверки присутствия отбрасывался, и сверять последующие вызовы
было не с чем. Сверка выполняется через общий helper
`BitrixTokenService.verifyApplicationToken(memberId, incomingToken)`
(`member_id` + `application_token`, timing-safe сравнение
`crypto.timingSafeEqual`) — ЛЮБОЙ будущий обработчик Bitrix24-событий,
кроме самого ONAPPINSTALL, обязан вызывать его перед обработкой запроса.

ХАРДЕНИНГ-ФИКС (static hardening pass): endpoint закрыт по умолчанию
fail-closed feature-флагом `BITRIX_INSTALL_ENABLED` (env, по умолчанию не
`"true"`) — пока флаг не включён явно, endpoint не пишет ничего в БД и
отвечает `{ result: false }`, независимо от `NODE_ENV`. Включать только
после проверки на тестовом портале. Дополнительно входные `domain`/
`member_id`/`access_token`/`refresh_token`/`application_token` проверяются
на соответствие документированному формату (regex по hostname/32-символьный
hex member_id/присутствие application_token) — без выдумывания
несуществующего протокола подписи; см. комментарии в
`src/bitrix/install.controller.ts`.

## 3. OAuth 2.0 (авторизация пользователей и обновление токена)

- Авторизационный код действует **30 секунд**.
- Обмен кода на токены — `POST https://oauth.bitrix.info/oauth/token/`
  с `grant_type=authorization_code`, `client_id`, `client_secret`, `code`.
- `access_token` — 1 час (3600 секунд) жизни, используется как параметр
  `auth`/`access_token` при вызове REST-методов.
- `refresh_token` — используется для получения нового `access_token` без
  повторного входа пользователя: тот же endpoint с
  `grant_type=refresh_token`.
- `member_id` — уникальный идентификатор портала (используется как
  бизнес-ключ `Tenant.portal`/`Tenant.memberId`).
- `domain` — домен конкретного портала (например, `company.bitrix24.ru`).

Источник: https://apidocs.bitrix24.com/settings/oauth/index.html,
https://apidocs.bitrix24.com/settings/how-to-call-rest-api/authorization.html

Отличие от вебхуков: **вебхуки** — постоянный код для серверных интеграций
без UI; **OAuth** обязателен для приложений с интерфейсом внутри портала
(наш случай) — даёт более широкий доступ и обязательную привязку к
конкретному пользователю Bitrix24.

Backend обязан:
- хранить `encryptedAccessToken` / `encryptedRefreshToken` (AES-256-GCM,
  ключ из секрета окружения, не в git);
- никогда не логировать токены и не отдавать их в frontend;
- проактивно обновлять `access_token` по `refresh_token` при истечении
  (`expiresAt`), с ретраем запроса.

## 4. Встраивание в интерфейс портала (placements)

Placements — заранее определённые точки Bitrix24, куда приложение может
встроить свой iframe (пункт левого меню, вкладка в CRM и т.д.).
Регистрация обработчика — метод `placement.bind`
(scope `placement`), список активных — `placement.list`.

Источник: https://apidocs.bitrix24.com/api-reference/widgets/placement-list.html

Для MVP используем:
- `DESKTOP_LEFT_MENU` / левое меню портала — основная точка входа в
  приложение (открывает наш SPA на всю ширину);
- в будущем: `CRM_*_DETAIL_TAB` — если потребуется показывать данные по
  объекту внутри карточки сделки/компании CRM (не входит в MVP).

**REQUIRES BITRIX24 TEST PORTAL VERIFICATION:** точный список доступных
placement-кодов и формат `PLACEMENT_OPTIONS`, приходящий в query при
открытии — нужно снять на реальном портале через `placement.list` и логи
первого открытия.

## 5. Пользователи и оргструктура

- `user.get` — получение списка/карточки пользователей портала (ФИО,
  email, `UF_DEPARTMENT`, должность, активность).
- `department.get` — организационная структура (подразделения),
  используется для построения дерева ответственных.
- Основной внешний идентификатор пользователя в нашей системе —
  `bitrixUserId` (число), НЕ email (email может отсутствовать/меняться).

`BitrixUserProvider.syncUsers(tenantId)` периодически (или по требованию
администратора) вызывает `user.get` и `department.get`, обновляя
локальные `User` записи (upsert по `bitrixUserId`).

## 6. Задачи и уведомления

- `tasks.task.add` — создание задачи в Bitrix24 (например, эскалация
  критического отставания ответственному РП).
- `im.notify` / `im.notify.system.add` — системные уведомления
  пользователю портала (короткие сообщения о событиях: замечание СК,
  просрочка, пакет готов к передаче).

`NotificationProvider`/`TaskProvider` — порты в домене; `RealBitrixAdapter`
вызывает эти методы, `MockBitrixAdapter` пишет уведомления в локальную
таблицу `Notification` и в лог.

## 7. Файлы (Bitrix24.Disk)

- `disk.folder.uploadfile` / `disk.storage.uploadfile` — загрузка файлов
  (фото инспекций, сканы АОСР, сертификаты материалов) в диск портала.
- Наша модель `Attachment`/`InspectionPhoto`/`ExecutiveDocument` хранит
  `fileProvider` (`BITRIX_DISK` | `LOCAL`) + `externalFileId`, не сам
  файл — это позволяет переключить провайдера без миграции данных.

**REQUIRES BITRIX24 TEST PORTAL VERIFICATION:** лимиты на размер файла и
формат ответа `disk.folder.uploadfile` на актуальной cloud-версии.

## 8. Scopes (права доступа приложения)

Минимально необходимый набор для MVP (запрашивается при установке):
`crm` — не требуется (мы не работаем со сделками); используем только:
`user_brief` / `user` (пользователи), `department` (оргструктура),
`placement` (встраивание), `task` (задачи), `im` (уведомления),
`disk` (файлы). Итоговый набор фиксируется в манифесте приложения при
регистрации на тестовом портале и должен быть минимальным.

## 9. Ограничения облачной (cloud) редакции

- Жёсткие лимиты частоты запросов (rate limiting) — на 2026 год для
  cloud-порталов действует пул запросов (окно из N запросов в секунду на
  портал), превышение возвращает `QUERY_LIMIT_EXCEEDED`. Backend обязан
  реализовать backoff/retry и очередь исходящих вызовов к Bitrix REST.
- On-premise (Bitrix24 «Коробочная версия») отличается версионированием
  API и доступностью некоторых batch-методов; архитектура приложения по
  умолчанию таргетируется на **cloud** и не полагается на
  on-premise-специфику. При необходимости коробочной версии — отдельная
  ревизия этого документа.

**REQUIRES BITRIX24 TEST PORTAL VERIFICATION:** точные текущие лимиты
rate limiting для конкретного тарифа тестового портала.

## 11. Следующий шаг для проверки на тестовом портале Bitrix24

1. Зарегистрировать локальное приложение на тестовом портале
   (`https://<portal>.bitrix24.ru/devops/`), получить `client_id`/`client_secret`.
2. Задать публичный `event_handler` URL (например, через ngrok/тестовый
   домен) на наш backend `/api/bitrix/install`.
3. Установить приложение, снять реальный payload `ONAPPINSTALL`, сверить
   с моком в `MockBitrixAdapter`.
4. Прогнать `RealBitrixAdapter` против тестового портала: `user.get`,
   `department.get`, `placement.bind`, `tasks.task.add`,
   `im.notify.system.add`, `disk.folder.uploadfile`.
5. Обновить этот документ фактическими данными и пометить пункты как
   `IMPLEMENTED AND VERIFIED` после успешной проверки.

**До выполнения этого шага приложение работает исключительно на
`MockBitrixAdapter` и не подключается к боевому/тестовому порталу —
это осознанное ограничение MVP согласно техническому заданию (раздел 56).**
