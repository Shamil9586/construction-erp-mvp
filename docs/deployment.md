# Развёртывание (тестовое окружение)

Статус: конфигурация написана и готова к использованию, но сборка
Docker-образов **не выполнялась** в песочнице разработки — нет доступа к
Docker Hub/npm registry (см. README «Известные ограничения среды»).
**REQUIRES CI/CD VERIFICATION** перед первым реальным использованием.

Согласно ТЗ, работа ведётся только в окружениях `development`/`test`, без
подключения к боевому Bitrix24, без публикации в Marketplace и без
изменения production-данных.

## Состав стека (docker-compose.yml)

| Сервис | Роль |
|---|---|
| `postgres` | PostgreSQL 16, персистентный volume `pgdata` |
| `backend` | NestJS API, применяет `prisma migrate deploy` при старте, затем слушает `:3000` |
| `frontend` | React SPA, собранный статикой и отданный через nginx, проксирует `/api/*` на `backend:3000` |
| `reverse-proxy` | Caddy — терминирует HTTPS (автоматический Let's Encrypt по домену `ERP_DOMAIN`), отдаёт `frontend` |

## Быстрый старт (test-окружение с доменом)

```bash
cp .env.example .env
# отредактировать .env: пароли, ENCRYPTION_KEY (openssl rand -base64 32),
# ALLOWED_BITRIX_DOMAIN, ERP_DOMAIN (реальный домен с DNS A-записью на сервер)
docker compose up -d --build
```

Приложение будет доступно по `https://$ERP_DOMAIN`. Backend — только
внутри docker-сети (`expose`, не `ports`) — снаружи недоступен напрямую,
только через reverse-proxy/frontend.

## Локальный запуск без домена/TLS (для разработки)

```bash
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build
```

- Frontend: `http://localhost:8080`
- Backend напрямую (для Swagger/отладки): `http://localhost:3000/api/docs`

Bitrix24 требует HTTPS для встраивания приложения в iframe placement —
этот режим годится только для просмотра экранов вне портала.

## Секреты

- Ничего секретного не коммитится (`.gitignore` исключает `.env*`, кроме
  `.env.example`).
- `ENCRYPTION_KEY` — обязателен для шифрования OAuth-токенов Bitrix24 в
  БД (AES-256-GCM). Смена ключа на проде инвалидирует уже сохранённые
  токены установленных порталов — требует переустановки приложения на
  портале.
- Для реального теста/прода секреты должны попадать в контейнер через
  секрет-хранилище оркестратора (Docker secrets, переменные CI/CD
  окружения, Vault), а не напрямую в `.env` на диске сервера — `.env` в
  этом репозитории задуман как шаблон для локальной/CI-подстановки.

## Миграции базы данных

`apps/backend/Dockerfile` выполняет `npx prisma migrate deploy` при
каждом старте контейнера — идемпотентная операция, безопасна для
повторного запуска, не выполняет `migrate reset` и не трогает
существующие данные (соблюдение прямого требования ТЗ о запрете
необратимых операций).

Для локальной разработки без Docker (с доступом к npm):

```bash
cd apps/backend
npm install
npx prisma migrate dev      # создаёт/применяет миграции, генерирует клиент
npx prisma db seed          # реалистичные сид-данные (prisma/seed.ts)
npm run start:dev
```

## package-lock.json — честный статус

В этом репозитории **нет** закоммиченного `package-lock.json` (ни в
корне, ни в `apps/*`, ни в `packages/*`). Это не забытый файл и не
столько лень, сколько прямое следствие ограничения среды разработки:
`registry.npmjs.org` заблокирован (HTTP 403 на уровне организационного
egress-прокси) в песочнице, где писался этот MVP, поэтому `npm install`
не может ни разу реально выполниться и honestly сгенерировать
`package-lock.json` с настоящими resolved-версиями и integrity-хешами.

Рукописная имитация `package-lock.json` (руками подставленные версии и
фейковые `integrity`-хеши) была бы хуже, чем его отсутствие: `npm ci`
проверяет каждый пакет по хешу из lock-файла и либо упадёт на
несовпадении (если хеш неверный), либо — что хуже — создаст ложное
ощущение проверенности там, где реальной проверки не было. Поэтому
файл не создавался руками.

**Что нужно сделать перед первой настоящей сборкой** (Docker или
локально), один раз, в среде с доступом к registry.npmjs.org:

```bash
npm install       # в корне монорепозитория — создаст корневой
                   # package-lock.json, покрывающий все workspaces
                   # (apps/backend, apps/frontend, packages/domain)
git add package-lock.json
git commit -m "chore: добавить package-lock.json"
```

После этого `npm ci` в обоих `Dockerfile` (`apps/backend/Dockerfile`,
`apps/frontend/Dockerfile`) и `verify`-независимая часть требования
«npm install из чистого репозитория» становятся выполнимыми буквально
как написано. До этого момента `docker build`/`npm ci` **не запустятся**
(`npm ci` требует существующего `package-lock.json` и завершится
ошибкой без него) — это единственная известная причина, по которой
Docker-сборка backend/frontend помечена `NOT VERIFIED` в этой среде,
а не гипотетическая.

## Здоровье сервиса

- `GET /health` — статический ответ (процесс жив).
- `GET /ready` — реальный `SELECT 1` к PostgreSQL (готовность принимать
  трафик). Использовать как healthcheck/readinessProbe в оркестраторе.

## Bitrix24: следующий шаг после развёртывания

Развёртывание тестового окружения — предпосылка, а не завершение
интеграции. Чтобы реально проверить работу в Bitrix24, нужно (с явного
разрешения пользователя, отдельным шагом — см. ограничения ТЗ):

1. Создать тестовый портал Bitrix24 (bitrix24.ru предоставляет бесплатный
   тестовый период) или использовать существующий не-боевой портал.
2. Зарегистрировать локальное приложение (Разработчикам → Другое →
   Локальное приложение), указать `https://$ERP_DOMAIN` как URL
   приложения и обработчик `POST /bitrix/install`.
3. Прописать полученные `BITRIX_CLIENT_ID`/`BITRIX_CLIENT_SECRET` в
   секреты окружения.
4. Установить приложение на тестовый портал, проверить `ONAPPINSTALL`,
   после чего переключить `BitrixInstallation.status` на `ACTIVE` —
   только тогда `BitrixGatewayService` начнёт использовать
   `RealBitrixAdapter` для этого тенанта вместо `MockBitrixAdapter`.

Подробности протокола — `docs/bitrix24-integration.md`.
