# MVP — сквозной тестовый сценарий (ТЗ §53)

Это не гипотетический план проверки — это описание того, что **реально
выполнялось** в этой среде разработки против настоящего сервера
PostgreSQL 16 и настоящего кода доменного слоя (`packages/domain`), плюс
что именно НЕ выполнялось и почему.

## Как проверить самостоятельно

```bash
# Требуется: PostgreSQL 16 (initdb/pg_ctl/psql в PATH) и Node 22 с
# глобально установленным `tsx` (npx tsx тоже подойдёт при наличии
# доступа к npm registry).
cd construction-erp
tsx verify/run.ts
```

`verify/run.ts` выполняет: пересоздание схемы (`verify/schema.sql`) →
сид реалистичных данных (`verify/seed.ts`) → полный сценарий ТЗ §53
(`verify/e2e.ts`) — и печатает пошаговый отчёт. Это не подмена
NestJS-backend'а: та же самая логика (`packages/domain`) подключена и в
`apps/backend` (см. `apps/backend/src/modules/*/*.module.ts` — каждый
сервис явно вызывает `ProgressCalculationService`,
`ScheduleStatusService`, `WorkTransitionPolicy`,
`PtoPackageValidationService`, `PotentialClosingService`,
`ObjectHealthService` напрямую, без заглушек).

## Что это доказывает

- Формулы прогресса/графика/светофора — не выдумка, а реально
  исполняющийся, протестированный код с точными числами на входе и выходе.
- Технологическая блокировка выдаёт содержательные причины на русском, а
  не просто `false` — ключевое требование ТЗ §20-21.
- Приёмка СК — атомарна и по-настоящему разблокирует зависимые работы.
- ПТО не даёт передать пакет в СДО, пока не выполнены реальные условия.
- Воронка «потенциал к закрытию» действительно обнуляется по мере
  прохождения этапов и корректно показывает застрявшую сумму на
  промежуточных шагах.
- Аудит действительно фиксирует весь путь.

## Что НЕ было проверено в этой среде (честно, явно)

| Что | Статус | Почему |
|---|---|---|
| Запуск реального `apps/backend` (NestJS) как процесса | **REQUIRES CI/CD VERIFICATION** | В песочнице разработки нет доступа к npm registry (см. README «Известные ограничения среды») — исходники написаны полностью и идиоматично, но `npm install`/`nest start` не выполнялись |
| Запуск реального `apps/frontend` (Vite dev server) | **REQUIRES CI/CD VERIFICATION** | Та же причина — код написан и вручную сверен с реальными сигнатурами backend-контроллеров (см. комментарии в `apps/frontend/src/pages/*.tsx`, ссылающиеся на конкретные сервисы backend) |
| Реальный Bitrix24-портал (OAuth, placements, users, tasks, notifications, disk) | **REQUIRES BITRIX24 TEST PORTAL VERIFICATION** | Работает только `MockBitrixAdapter`; `RealBitrixAdapter` написан по актуальной документации (см. `docs/bitrix24-integration.md`), но не вызывался против реального портала — явное требование ТЗ: без разрешения не подключаться к боевому порталу |
| Docker-сборка образов (`docker-compose.yml`) | **REQUIRES CI/CD VERIFICATION** | Нет доступа к Docker Hub/npm registry в этой среде — Dockerfile'ы написаны по стандартным паттернам |
| Jest-интеграционные тесты backend (supertest) | Не написаны в этой итерации | Приоритет был отдан сквозной проверке domain-слоя против реальной БД, которая покрывает бизнес-логику полнее, чем HTTP-уровень; backend-контроллеры — тонкие обёртки над уже проверенными сервисами |

Ничто из вышеперечисленного не было представлено как «сделано» без этой
оговорки — см. таблицу статусов в корневом `README.md`.
