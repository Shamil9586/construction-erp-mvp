# ADR-0001: Общая архитектура системы управления строительством

Статус: **Принято**
Дата: 2026-09-14

## Контекст

Строительная компания ведёт производственный учёт (объекты, СМР, строительный
контроль, ПТО, СДО, финансовое закрытие) в Excel и разрозненных таблицах
Bitrix24. Требуется цифровое производственное ядро с единым источником
истины, автоматическим расчётом план/факта, светофором объектов и
исполнительным дашбордом для генерального директора.

Bitrix24 уже используется компанией как корпоративная оболочка (пользователи,
организационная структура, задачи, диск, уведомления).

## Решение

Мы **не** строим систему поверх сделок/лидов/смарт-процессов/универсальных
списков Bitrix24 и **не** переносим Excel в браузер.

Мы создаём:

```
Bitrix24 (корпоративная оболочка и интеграционная платформа)
   │  OAuth / REST / placements / events
   ▼
Встраиваемое приложение (Local Application)
   │
   ├── Frontend: React + TypeScript + Vite (SPA, встраивается в iframe placement)
   ├── Backend: Node.js + TypeScript + NestJS (собственный REST API)
   └── Database: PostgreSQL (собственная предметная модель)
```

Bitrix24 используется только там, где это официально поддерживается и
целесообразно: идентификация/OAuth, оргструктура (users/departments),
уведомления, задачи, Bitrix24.Disk для хранения файлов, placements для
встраивания экранов, события (ON_APP_INSTALL и т.п.).

Основная предметная модель строительства (объекты, работы, строительный
контроль, ПТО, СДО, финансовое закрытие) живёт **только** в нашей
PostgreSQL и не хранится в сущностях Bitrix24. Ядро домена не должно
напрямую зависеть от Bitrix REST — доступ идёт через порты/адаптеры
(`BitrixUserProvider`, `NotificationProvider`, `TaskProvider`,
`FileStorageProvider`), с `MockBitrixAdapter` для разработки без
реального портала и `RealBitrixAdapter` для продакшена.

## Причины

1. **Гибкость домена.** Работы, зависимости, светофор, план/факт,
   технологические блокировки — это предметная логика, которую неудобно
   и небезопасно моделировать смарт-процессами/UF-полями Bitrix24: нет
   нормальных транзакций, сложных агрегатов, версионирования и
   произвольных вычисляемых показателей.
2. **Производительность и масштабируемость.** Дашборд генерального
   директора требует тяжёлой агрегации (десятки объектов × сотни работ ×
   история прогресса). Это задача для SQL/PostgreSQL с индексами, а не
   для REST-вызовов к CRM.
3. **Безопасность типов и данных.** PostgreSQL + Prisma + DTO-валидация
   дают строгую схему, внешние ключи, decimal для денег, оптимистичную
   конкурентность (version). Bitrix24 UF-поля этого не дают.
4. **Независимость от портала.** Приложение должно работать (на
   MockBitrixAdapter) даже без доступа к боевому порталу — для
   разработки, тестов и демонстраций.
5. **Читаемость для руководства.** Экран «Требует внимания» с денежным
   эффектом и конкретной причиной — это не то, что можно получить из
   стандартных виджетов CRM без кастомной агрегации.

## Альтернативы (отклонены)

- **Смарт-процессы Bitrix24** — отклонено: нет нормальных многошаговых
  транзакций (приёмка СК → разблокировка следующей работы → аудит),
  сложно моделировать иерархию работ и историю прогресса.
- **Excel/Google Sheets + надстройки** — отклонено явно техническим
  заданием: не решает задачу автоматического светофора и агрегации по
  портфелю объектов.
- **Полностью независимое SaaS без Bitrix24** — отклонено: компания уже
  живёт в Bitrix24 (пользователи, коммуникации), дублировать
  идентификацию и оргструктуру нецелесообразно.

## Последствия

- Нужен отдельный backend с собственной авторизацией сессии,
  синхронизированной с Bitrix24 (bitrixUserId как основной внешний ключ
  пользователя).
- Нужен слой адаптеров для Bitrix REST, чтобы не блокировать разработку
  на отсутствии тестового портала.
- Архитектура готова к multi-tenant (несколько порталов Bitrix24) с
  первого дня, даже если эксплуатация начинается с одного портала.
- Приложение целится в облачную (cloud) редакцию Bitrix24; ключевые
  различия cloud/on-premise зафиксированы в
  [docs/bitrix24-integration.md](./bitrix24-integration.md).

## Ориентировочный технологический стек

| Слой | Технология |
|---|---|
| Frontend | React 18, TypeScript, Vite, React Router, TanStack Query, React Hook Form, Zod, Ant Design (enterprise UI) |
| Backend | Node.js 22, TypeScript, NestJS |
| DB | PostgreSQL 16 |
| ORM | Prisma |
| API | REST + OpenAPI/Swagger |
| Infra | Docker, Docker Compose, dotenv, Prisma Migrate |
| Тесты | Jest (unit/integration), supertest (E2E HTTP) |

Отклонения от этого стека допустимы при технической необходимости, но
базовая архитектура (frontend + backend + PostgreSQL + Bitrix-адаптер)
не пересматривается без явной технической причины.
