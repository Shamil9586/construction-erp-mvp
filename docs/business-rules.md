# Бизнес-правила (производственное ядро)

Все правила ниже реализованы как чистые функции в `packages/domain/`
(без зависимостей от NestJS/Prisma/React) и покрыты юнит-тестами
(`packages/domain/test/*.test.ts`, 44 теста, все проходят), а затем
дополнительно проверены сквозным сценарием против настоящего PostgreSQL
(`verify/e2e.ts`, 22 шага, все проходят — см. `docs/mvp-test-scenario.md`).
Это не описание того, что "должно быть" — это код, который реально
исполнялся и давал показанные ниже цифры.

## 1. Прогресс работы (`ProgressCalculationService`)

```
rawProgressPercent = actualQuantity / plannedQuantity * 100
progressPercent    = min(100, rawProgressPercent)   // для UI/светофора
isOverperformed     = rawProgressPercent > 100
```

Процент **не вводится вручную** — РП вносит только накопительный
фактический объём (`actualQuantity`), процент всегда пересчитывается.
Пример из E2E: план 20 т, факт 10 т → 50% (ТЗ §53 шаг 7).

## 2. График план/факт (`ScheduleStatusService`)

Плановый % на сегодня считается линейно между `plannedStartDate` и
`plannedFinishDate` (MVP; архитектура допускает заменить на недельный
план-график без изменения интерфейса потребителей — следующая итерация).

```
plannedProgressPercent = clamp(0, 100, (today - start) / (finish - start) * 100)
varianceP  = actualProgressPercent - plannedProgressPercent   // п.п.
```

Пороги (настраиваемые, `RiskThresholds`, НЕ хардкод — читаются из
`risk_settings` в БД, ТЗ: «не хардкодить пороги»):

| Статус | Условие | По умолчанию |
|---|---|---|
| `DONE` | `actualProgressPercent >= 100` | — |
| `ON_TRACK` | `varianceP >= greenVarianceThreshold` | ≥ -5 п.п. |
| `BEHIND` | `yellowVarianceThreshold <= varianceP < greenVarianceThreshold` | от -15 до -5 п.п. |
| `CRITICAL` | `varianceP < yellowVarianceThreshold` | < -15 п.п. |

`delayDays` — эвристическая оценка потерянных дней при текущем темпе
относительно линейного плана: `round(|varianceP| / 100 * spanDays)`.

Пример из E2E (шаги 8-9): работа с планом на сегодня 75%, факт 50% →
`varianceP = -25 п.п.`, `scheduleStatus = CRITICAL`, `delayDays = 10`.

## 3. Технологические переходы (`WorkTransitionPolicy`)

Работа не может начаться, пока не выполнены условия по всем
FINISH_TO_START-зависимостям:

- если `requiresAcceptance = true` — предшествующая работа должна быть
  **принята** строительным контролем (`predecessorLatestInspectionStatus
  === ACCEPTED`);
- по предшествующей работе не должно быть непогашенных **критических**
  замечаний (`predecessorHasOpenCriticalIssues`);
- не должно быть недостающего обязательного документа
  (`predecessorMissingRequiredDocument` — расширяется вместе с ПТО).

`canStartWork()` возвращает **конкретные текстовые причины**, а не просто
`false` — это прямое требование ТЗ §20-21. Пример из E2E (шаг 13):

```
canStartWork = false
причины:
  «Армирование фундамента Ф-1» не принята строительным контролем
   (последний статус проверки: ISSUES_FOUND).
  По «Армирование фундамента Ф-1» есть непогашенное критическое замечание.
```

После устранения замечания и приёмки СК (шаг 17) та же проверка
возвращает `canStartWork = true`, и следующая работа («Бетонирование»)
разблокируется автоматически.

## 4. Светофор объекта (`ObjectHealthService`)

Агрегирует несколько сигналов в один статус объекта:

1. `GRAY` — если у объекта нет работ **или** последнее обновление факта
   старше `staleProgressAfterDays` (по умолчанию 10 дней) — «недостаточно
   данных», это не оптимизм и не ошибка, а честный сигнал ГД, что данные
   протухли.
2. Иначе — эскалация по нарастающей на основе: худшего
   `scheduleStatus`/`varianceP`/`delayDays` среди работ объекта,
   количества открытых **критических** замечаний СК, просроченных
   замечаний, заблокированных работ, backlog ПТО/СДО.
3. `RED`, если есть хотя бы один критический сигнал (критическое
   отставание, открытое критическое замечание, значительный backlog);
   `YELLOW` — при менее острых сигналах; иначе `GREEN`.

Пересчитывается **синхронно** после каждой операции, способной изменить
состояние объекта (факт, приёмка/отклонение СК, создание замечания) —
`ObjectsService.recalculateHealth()`, реальный вызов, не фоновая задача.

## 5. Строительный контроль (СК)

- `ConstructionInspection` проходит через статусы: `WAITING` →
  `IN_REVIEW`/`ISSUES_FOUND` → (после устранения) `REINSPECTION` →
  `ACCEPTED` | `REJECTED`.
- Замечание (`InspectionIssue`) имеет критичность `MINOR` | `CRITICAL`.
  **Открытое `CRITICAL`-замечание блокирует приёмку целиком** —
  `InspectionsService.accept()` выбрасывает `BadRequestException`, если
  есть хоть одно незакрытое критическое замечание (ТЗ §47).
- Приёмка — **атомарная транзакция** (`prisma.$transaction`): статус
  проверки → `ACCEPTED`, `objectWork.acceptedQuantity` обновляется,
  закрываются замечания в статусе `READY_FOR_VERIFICATION`, пишется
  AuditLog, пересчитывается разблокировка зависимых работ через
  `WorkTransitionPolicy`, пересчитывается светофор объекта — либо всё,
  либо ничего.

## 6. ПТО / исполнительная документация (ИД)

- Документ (`ExecutiveDocument`, 6 типов: АОСР, исполнительная схема,
  сертификат, паспорт, протокол испытаний, прочее) **всегда стартует со
  статуса `DRAFT`** — автоматически сформированный документ не считается
  юридически подтверждённым, пока ПТО его не одобрит (`approveDocument`,
  ТЗ §27).
- Пакет ИД (`ExecutiveDocumentPackage`) собирается из нескольких
  документов и **нельзя передать в СДО**, пока `PtoPackageValidationService`
  не подтвердит: по каждой входящей в пакет работе документы в статусе
  `READY`/`APPROVED` (если `workType.requiresExecutiveDocs`), и материалы
  с действующим сертификатом, если работа их требует
  (`workType.requiresMaterials`). Если проверка не пройдена —
  `transferToSdo()` бросает `BadRequestException` со списком конкретных
  причин (не просто "нельзя").
- Только после успешной передачи создаётся `SdoCase` со статусом
  `TRANSFERRED` — это единственная точка входа СДО в работу по объекту.

## 7. СДО (сметно-договорной отдел)

Система **намеренно не замещает** сметный комплекс (Гранд-Смета) и не
формирует КС-2 — это прямое ограничение ТЗ. `SdoCase` — это просто
"дело", фиксирующее факт передачи и позже — стоимость, рассчитанную
**вне системы** и введённую вручную (`SdoService.close()` создаёт
`FinancialClosing`). Обе операции — в транзакции.

## 8. Потенциал к закрытию — «где застряли деньги» (`PotentialClosingService`)

Центральная метрика для генерального директора. По каждой работе с
`estimatedCost` считается ставка `rate = estimatedCost / plannedQuantity`
и денежная стоимость на каждой стадии воронки:

| Стадия | Смысл |
|---|---|
| 1 | Физически выполнено, но **не принято** строительным контролем |
| 2 | Принято СК, но **ИД не готова** |
| 3 | ИД готова, но **не передано** в СДО |
| 4 | Передано в СДО, но **ещё не рассчитано** (нет `calculatedValue`) |
| 5 | Рассчитано СДО, но **ещё не закрыто** финансово |

`potentialClosingValue = Σ(стадия 1..5)` — сумма денег, "застрявших" на
любом этапе воронки. Пример из E2E (шаг 24): после полного прохождения
всех этапов по тестовой работе — `potentialClosing: 900 000 ₽ → 0 ₽`,
`object.healthStatus: GREEN`. До этого на промежуточных шагах сумма явно
распределена по стадиям 1-3, что и позволяет ответить на вопрос
«на каком именно этапе зависли деньги».

## 9. Эскалация (`EscalationService`)

По количеству дней подряд в статусе `RED`:

```
< escalateToTechDirectorAfterDays (7)     → NONE
>= 7  и < escalateToGeneralDirectorAfterDays (14) → DEPARTMENT_HEAD, затем TECHNICAL_DIRECTOR
>= 14                                      → GENERAL_DIRECTOR
```

Дедупликация уведомлений — `buildNotificationDedupKey(eventType, entityId,
date)` → `` `${eventType}:${entityId}:${YYYY-MM-DD}` `` — уникальный
constraint `(tenantId, dedupKey)` в таблице `notifications` физически не
даёт продублировать одно и то же уведомление в один день.

## 10. Оптимистичная блокировка

`ConstructionObject.version` и `ObjectWork.version` — целочисленный
счётчик. Любое обновление объекта требует передать текущий `version`;
если он не совпадает с актуальным — `409 ConflictException`
(«Объект был изменён другим пользователем — обновите страницу»), ТЗ §48.

## 11. Аудит

Каждая операция, меняющая состояние (факт, приёмка/отклонение СК,
замечание, документ ПТО, передача в СДО, финансовое закрытие, изменение
объекта), пишет запись в `AuditLog` (`entityType`, `entityId`, `action`,
`oldValue`/`newValue`, `userId`, `createdAt`). Обычный пользователь не
может изменить или удалить запись — в `AuditController` нет
`PATCH`/`DELETE`. Пример из E2E (шаг 25): 16 записей аудита по одному
тестовому объекту, покрывающих весь путь от создания работы до
финансового закрытия.

## 12. Деньги и объёмы — только Decimal

Все денежные и количественные поля в схеме — `Decimal` (Prisma
`@db.Decimal(...)`), никогда `Float`, чтобы избежать ошибок округления
при суммировании (ТЗ §46).
