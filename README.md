# Construction ERP — производственное ядро для строительной компании

Встраиваемое в Bitrix24 приложение с собственным frontend/backend/БД,
закрывающее пайплайн: **Планирование → СМР → факт → строительный
контроль → исполнительная документация (ПТО) → передача в СДО →
финансовое закрытие → управленческая аналитика**. Главный потребитель —
генеральный директор, которому за 1-2 минуты должно быть понятно: какие
объекты отстают и насколько, кто виноват, где именно застряли деньги и
что нужно сделать.

Архитектурное решение и его обоснование — [ADR-0001](docs/adr-0001-architecture.md).
Bitrix24 используется как корпоративная оболочка (идентификация, оргструктура,
уведомления, задачи, диск, встраивание экранов) — **не** как хранилище
предметной модели. Предметная логика живёт в собственной PostgreSQL и
никогда не смоделирована через сделки/смарт-процессы/UF-поля.

## Что исправлено в этой итерации (technical hardening pass)

Список — не для рекламы, а чтобы было видно, что "код выглядит полным"
и "код реально работоспособен" — разные утверждения, и в прошлой
итерации было доказано только первое. Ниже — что нашлось и было
реально исправлено (не просто описано) при попытке довести до второго:

1. **Критический баг DI**: `BitrixAuthGuard`/`PermissionsGuard`
   нигде не были зарегистрированы как NestJS provider (`grep` по всему
   дереву модулей подтвердил ноль совпадений) — при реальном запуске
   backend упал бы на первом же запросе к защищённому эндпоинту.
   Исправлено: `src/modules/auth/auth.module.ts` (`@Global()`).
2. **Дублирование `PrismaService`**: 13+ модулей независимо объявляли
   `PrismaService` в своих `providers` — каждый создавал свой
   `PrismaClient`/пул соединений вместо одного на процесс. Исправлено:
   `src/common/prisma.module.ts` (`@Global()`), локальные регистрации
   убраны.
3. **`packages/domain/package.json`** указывал `main`/`types` на
   `src/index.ts` — production-процесс (без ts-node/tsx) не смог бы
   импортировать пакет. Исправлено на `dist/*`, добавлен `exports`.
   Проверено реальной сборкой + `require()`.
4. **`ObjectWork`** использовался в коде (`financial`/`inspections`
   модули) с тремя полями (`acceptedQuantity`,
   `executiveDocsReadyQuantity`, `transferredToSdoQuantity`),
   отсутствовавшими в `schema.prisma` — добавлены, плюс дописана
   бизнес-логика в `pto.module.ts`, которая их реально заполняет по
   ходу воронки потенциального закрытия (без этого поля были бы
   вечными нулями даже при наличии в схеме).
5. **Авторизация**: демо-заголовки `X-Tenant-Id`/`X-Bitrix-User-Id`
   теперь работают только в `AUTH_MODE=demo`, который **запрещён**
   (fail-closed, `InternalServerErrorException`) при
   `NODE_ENV=production`. Production-режим (`AUTH_MODE=bitrix`)
   проверяет HMAC-подписанный сессионный токен
   (`session.util.ts`, 6/6 реально выполненных тестов). Frontend
   спрашивает `GET /auth/mode` и скрывает demo-переключатель личности,
   если backend не в demo-режиме.
6. **`GET /users`** требовал `ADMIN_USERS` — из-за чего ни один
   реальный пользователь, кроме ADMIN, не мог получить список
   сотрудников для простейших операций (выбрать РП при создании
   объекта). Понижено до `OBJECT_VIEW` (есть у всех ролей).
7. **Prisma-миграция**: написана и реально применена к заведомо пустой
   базе PostgreSQL 16 (`apps/backend/prisma/migrations/20260914120000_init/`).
8. **Frontend**: вкладки «Материалы», «СДО», «ПТО», «Строительный
   контроль» карточки объекта заменены с информационных
   заглушек/таблиц-только-на-чтение на формы, вызывающие уже
   существовавшие backend-эндпоинты; добавлены создание/редактирование
   объекта и добавление работы.

Полный формальный отчёт со статусом каждой отдельной команды — в конце
этого файла, раздел «Итоговый отчёт о проверке».

## Быстрый старт

### Вариант A — как задумано (нужен npm/Docker)

```bash
cp .env.example .env    # отредактировать пароли/ключи
docker compose up -d --build
```

См. [docs/deployment.md](docs/deployment.md) для полного описания, включая
локальный режим без домена/TLS.

### Вариант B — проверка бизнес-логики без npm (то, что реально
### выполнялось при разработке этого MVP в песочнице)

Требуется только PostgreSQL 16 (`initdb`/`pg_ctl`/`psql`) и `tsx`
(глобально или через `npx`):

```bash
tsx verify/run.ts
```

Поднимает схему, засеивает реалистичные данные, прогоняет полный
сценарий ТЗ §53 против настоящей БД и печатает пошаговый отчёт (пример
вывода — [docs/mvp-test-scenario.md](docs/mvp-test-scenario.md)).

## Структура репозитория

```
apps/backend/     NestJS REST API (13 бизнес-модулей + auth/prisma/health/bitrix, Prisma на 29 моделей, Bitrix-адаптеры)
apps/frontend/    React + TS + Vite + Ant Design SPA
packages/domain/  Доменная бизнес-логика — 0 зависимостей от фреймворков,
                  используется и backend'ом, и verify/-harness'ом
verify/           Локальный верификационный harness (реальный PostgreSQL,
                  без npm install) — доказательство работоспособности
                  доменного слоя в этой песочнице
infra/            Caddyfile (HTTPS-реверс-прокси для теста)
docs/             Архитектура, домен-модель, ER-диаграмма, бизнес-правила,
                  права доступа, интеграция с Bitrix24, тестовый сценарий,
                  развёртывание
docker-compose.yml, docker-compose.local.yml, .env.example
```

## Явные ограничения v1 (осознанно вне рамок MVP)

Импорт из Excel (архитектурно заложен, но не реализован — заменён
реалистичными сид-данными), BIM, сложное CPM/PERT-планирование,
AI-анализ фото, OCR документов, полноценная юридически значимая АОСР с
ЭЦП, offline-режим мобильного приложения, глубокая интеграция с ERP,
полноценный сметный комплекс/генерация КС-2 (система намеренно не
заменяет Гранд-Смету). Архитектура (порты/адаптеры, чистый доменный
слой) допускает добавление всего перечисленного без переписывания ядра.

## Безопасность и производственные ограничения (соблюдены)

Без отдельного разрешения: не подключались к боевому Bitrix24, не
публиковали приложение в Marketplace, не изменяли production-данные, не
выполняли необратимых операций. Вся разработка — на `MockBitrixAdapter`
и локальном PostgreSQL. Секреты не хранятся в git (`.env.example` —
только шаблон). Токены Bitrix24 шифруются AES-256-GCM и не логируются.
